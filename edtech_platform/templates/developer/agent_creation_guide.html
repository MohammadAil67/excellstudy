Building an AI Agent

Complete developer reference — Part A. Covers endpoints, the manifest, I/O types, MCP data access, and hard constraints.

Spec v2.0 ~20 min read Docker-based
A.1

What you're building

An agent is a Docker container exposing a small, fixed set of HTTP endpoints. The platform never inspects or runs your code directly — it only ever talks to your container over HTTP, at the routes described below. Your language, framework, internal logic, and LLM choice are entirely up to you.

Your container just needs to: 1. Listen on a port 2. Respond correctly at /invoke, /health, /capabilities 3. Return JSON in the platform's expected shape
A.2

Required endpoints

Every agent must expose all three. The validation pipeline checks all three before your agent ever goes live, and Kubernetes continuously checks /health afterward.

POST /invoke
Called every time a learner submits input to your agent.
Request body you will receive:
{ "input": { /* shape depends on your declared input_type — see A.4 */ }, "context": { "learner_id": "8821" } }
Response you must return:
{ "content": [ { "type": "verdict", "correct": true, "confidence": 0.92, "summary": "Correct!" } ] }
Each block's type must be an approved output type (see A.5). Blocks with unrecognised types are silently dropped by the platform's renderer — double-check spelling and casing.
GET /health
Called frequently by both the pipeline and Kubernetes. Must respond quickly with no side effects — don't write to a database, don't call an LLM here. If this stops responding, Kubernetes restarts your container automatically.
{ "status": "ok" }
GET /capabilities
Returns a live description of what your agent supports, matching what you registered in the dev portal (see A.3).
{ "input_type": "image_upload", "output_types": ["verdict", "annotated_image"] }
A.3

manifest.json

Every submitted image must include manifest.json (typically at /app/manifest.json). This describes your agent to the platform without requiring anyone to read your code.

{ "name": "biology-drawing-checker", "version": "1.0.0", "subject_areas": ["biology"], "age_groups": ["12-18"], "input_type": "image_upload", "output_types": ["verdict", "annotated_image"], "options": [], "endpoints": { "invoke": "/invoke", "health": "/health", "capabilities": "/capabilities" } }
FieldNotes
nameDisplay name
versionSemver only: 1.0.0, not v1 or 1.0
input_typeExactly one value — see A.4
output_typesOne or more values — see A.5
subject_areas / age_groupsMarketplace search/filter only
optionsOnly used when input_type is multiple_choice — see A.4
This file must match your portal registration exactly (Part B). The pipeline cross-checks your container's manifest against your portal registration — a mismatch is a rejection, not a silent overwrite in either direction. If you change your agent's real input/output behaviour, update both the portal registration and this file together, then resubmit.
A.4

Choosing your input type

Declare exactly one. This determines what input component learners see, and what shape input takes in your /invoke request.

input_typeLearner seesYou receive
text_with_units Text field { "value": "30 m/s" }
number Number field { "value": 42 }
image_upload File / drawing upload { "image_url": "https://..." }
multiple_choice Radio buttons { "selected_index": 2 }
free_text Larger text area { "value": "..." }
If input_type is multiple_choice, you must also provide options in your manifest — a list of {label, value} objects the platform renders as radio buttons.
"options": [ { "label": "1/2", "value": 0 }, { "label": "3/4", "value": 1 } ]
Note on images: image_url is always a URL, never raw image bytes. The learner's browser uploads the file to platform storage first and only sends you the resulting URL. Download the image yourself inside your /invoke handler if you need to inspect pixel data.
A.5

Choosing your output types

Declare one or more. Every block in your /invoke response's content array must use one of these type values with the listed required fields.

typeRequired fieldsUse for
verdict correct (bool), summary (str), confidence (float, optional) Right/wrong feedback
annotated_image image_url (str), markup (list of {x, y, label, status}) Marked-up image feedback
score value (num), max (num), breakdown (dict, optional) Numeric / graded feedback
diff learner_answer, correct_answer, explanation Comparing to a correct answer
text value (str) Plain explanation — safe fallback
step_list steps (list of str) Worked-solution walkthroughs
comparison headers (list), rows (list of lists) Side-by-side tables
hint value (str), reveal_order (int) Progressive hints
Example — physics realism checker:
{ "content": [ { "type": "verdict", "correct": false, "confidence": 0.87, "summary": "Not realistic" }, { "type": "text", "value": "A car accelerating at 50 m/s² would exceed highway speed in under a second." } ] }
Example — biology drawing checker:
{ "content": [ { "type": "annotated_image", "image_url": "https://.../learner-upload-123.png", "markup": [ { "x": 120, "y": 80, "label": "correct: nucleus", "status": "correct" }, { "x": 300, "y": 200, "label": "missing: cell wall", "status": "missing" } ] }, { "type": "verdict", "correct": false, "summary": "Mostly correct — one structure missing" } ] }
A.6

Accessing platform data from your agent

Your container has no database credentials and no direct network path to Postgres, Redis, or Neo4j. If you need learner or curriculum data, you call the platform's MCP servers as an MCP client, using the credential (AGENT_KEY) injected into your container automatically at deploy time.

from fastmcp import Client import os AGENT_KEY = os.environ["AGENT_KEY"] LEARNER_CONTEXT_MCP_URL = os.environ["LEARNER_CONTEXT_MCP_URL"] async def get_learner_profile(learner_id: str) -> dict: async with Client(LEARNER_CONTEXT_MCP_URL) as client: return await client.call_tool( "get_learner", {"learner_id": learner_id, "agent_key": AGENT_KEY}, )
Available MCP servers and tools:
ServerToolsNotes
Learner Context get_learner, write_progress Third-party agents get a filtered profile (no mood/session data) and a capped write delta (±10 vs ±100 for built-in agents). get_session is built-in-agents-only and will reject you.
Knowledge Graph get_prerequisites, get_next_concepts, get_concept No RBAC distinction — curriculum structure isn't sensitive.
Content search_content, get_course, get_module Used for RAG — retrieving relevant material to ground your LLM.
write_progress example:
await client.call_tool("write_progress", { "learner_id": learner_id, "agent_key": AGENT_KEY, "updates": {"physics": 5}, # delta, not absolute # exceeding your cap raises an error, # it does not silently clamp })
A.7

Hard constraints — never do these

Violations of any of the following cause automatic pipeline rejection or immediate suspension.

  • Never return raw HTML, CSS, or JavaScript in any content block. All rendering is done by the platform's own components.
  • Never invent a type value outside the A.5 table — unknown types are silently dropped from what learners see.
  • Never attempt a direct database connection. Use the MCP servers (A.6) for any platform data you need.
  • Never run your container process as root — the pipeline's security scan checks and rejects this.
  • Never do slow or stateful work inside /health.
  • Never hardcode secrets or API keys into the image.
  • Never assume a write to write_progress silently succeeds if it exceeds your delta cap — handle the error.
  • Never call get_session as a third-party agent — always rejected.
A.8

Pre-submission checklist

Go through this list before pushing your image. Every item here maps to something the pipeline will check.

  • /invoke, /health, /capabilities all respond correctly when tested locally
  • manifest.json is present, valid JSON, and matches your /invoke behaviour exactly
  • input_type and output_types in the manifest match what you'll enter in the dev portal
  • If input_type is multiple_choice, options is populated
  • Every output block your agent returns matches the required fields in A.5
  • Container does not run as root
  • No hardcoded secrets baked into the image
  • Tested with docker run + curl against all three endpoints yourself
