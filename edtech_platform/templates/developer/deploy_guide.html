Pushing and Deploying Your Agent

Part B — complete walkthrough. Register first, build and push your image, watch the pipeline, and go live.

Deploy Guide Register-first flow ghcr.io registry
Register-first flow You declare your agent in the dev portal before you push any code. The pipeline then validates that your pushed container actually matches what you declared.
1
B.1 — Register the agent in the dev portal
Do this before building or pushing anything.
  1. Log into the dev portal
  2. Go to "Register a new agent"
  3. Fill in: name, input_type (single choice, from A.4), output_types (one or more, from A.5), subject_areas, age_groups, capabilities
  4. Submit
This creates a pending registration and auto-generates your agent's slug — a unique identifier of the form {your-namespace}-{agent-name}, e.g. alice-biology-drawing-checker. The confirmation page shows you the exact commands to use next, built from that slug.
Register an Agent
2
B.2 — Generate a registry push token
One-time, per developer. You'll use this to authenticate docker push.
  1. Go to github.com/settings/tokens?type=beta
  2. Generate new token
  3. Resource owner: the platform's GitHub org (or account)
  4. Permissions → Packages: Read and write
  5. Copy the token — you'll use it in B.4
3
B.3 — Build your agent & prepare manifest.json
Follow Part A — the creation guide to build your agent image.
Use the manifest.json generator — don't hand-write it. After registering your agent (B.1), go to your agent's Pipeline Status page in the dev portal. Open the manifest.json Generator card — it outputs a pre-filled, copy-ready manifest.json built directly from your registered data. This guarantees the schema check will pass.
The pipeline cross-checks input_type and output_types in your manifest.json against what you registered in B.1 — they must match exactly, or the schema check will reject your image with a specific mismatch message. Do not edit these two fields after copying the generated manifest.
Drop the generated file at /app/manifest.json inside your Docker image (e.g. via a COPY manifest.json /app/manifest.json line in your Dockerfile).
4
B.4 — Tag and push, using your exact slug from B.1
Replace {platform-org}, {your-slug}, YOUR_GITHUB_USERNAME, and YOUR_TOKEN_FROM_B2 with your values.
# Build docker build -t ghcr.io/{platform-org}/{your-slug}:v1 . # Authenticate docker login ghcr.io -u YOUR_GITHUB_USERNAME -p YOUR_TOKEN_FROM_B2 # Push docker push ghcr.io/{platform-org}/{your-slug}:v1
The image tag must exactly match your registered slug. Pushing under a different name will fail — the pipeline looks up your pending registration by this exact slug and will reject the push if no matching pending row exists.

Schema check — pulls manifest.json from your image, cross-checks input_type/output_types against what you registered in B.1. Mismatch = rejected with a specific message.

Security scan — CVE dependency scan + confirms your container doesn't run as root.

Smoke test — spins up your container, calls /health and /invoke with a synthetic request, validates the response shape matches your declared output types.

Deploy — on success, your container is deployed into your own isolated, quota-limited namespace and registered on the platform.

B.6

If a step fails

You'll see the specific failing step and a detailed reason on the pipeline status page. For example:

Schema check failed: Container declares input_type='number' but you registered 'text_with_units' in the dev portal. These must match.

Fix the mismatch (either your code/manifest, or your portal registration — whichever is actually wrong), then push a new version tag (e.g. :v2) to resubmit.

You do not need to re-register in the portal for a version bump of the same agent — only if you're changing its declared input_type/output_types from scratch.
B.7

Updating an already-live agent

Push a new version tag. The full pipeline runs again before replacing the live version — it does not go live immediately on push.

docker build -t ghcr.io/{platform-org}/{your-slug}:v2 . docker push ghcr.io/{platform-org}/{your-slug}:v2
B.8

Quick end-to-end verification, once live

A successful response here confirms your agent is reachable and responding correctly through the platform's real invocation path, not just standalone.

curl -X POST https://{platform-domain}/api/v1/agents/{your-slug}/invoke/ \ -H "Content-Type: application/json" \ -d '{"input": {"value": "test"}, "context": {"learner_id": "test-001"}}'
